### 1) Batched paired eval: highest ROI

Yes, you can batch frames within one SNR **and still preserve paired McNemar correctness**.

The safe pattern is:

1. **pre-generate** a deterministic frame bank: `(channel, bits, noise)` for frame `fi`
2. store either full tensors or per-frame seeds
3. run **both classical and learned** on the exact same frame bank
4. batch only at the compute stage

That preserves pairing. What you should **not** do is let batched generation implicitly change the global RNG stream and then assume it is equivalent to old one-frame-at-a-time runs.

### Pseudocode

```python
# CPU-side deterministic frame bank
bank = []
for fi in range(max_frames):
    seed = base_seed + fi
    frame = simulate_one_frame(seed=seed, snr_db=snr_db)
    bank.append(frame)

for batch in chunk(bank, B=16):
    y, meta = collate(batch)  # pinned CPU memory
    y = y.to("cuda", non_blocking=True)

    out_cls = run_pipeline(y, meta, learned=False)
    out_lrn = run_pipeline(y, meta, learned=True)

    update_paired_counts(out_cls, out_lrn, meta)
```

### 2) Cache what is actually static

Your suspicion is slightly mis-aimed: **Phi is not channel-dependent** in the first pilot-only pass. It depends on the transmit waveform/system, not on the realized channel.

So:

* **cache pilot-only `Phi_pilot` once**
* reuse it across all frames and SNRs
* for later data-aided rounds, full caching is not possible because `x_soft` changes, but you can still cache static index maps / phase ramps / base templates

So the correct answer is:

> **Do not cache "Phi per-channel realization." Cache the pilot-only sensing matrix globally, and cache reusable templates for the data-aided builder.**

### 3) Mixed precision: safe and unsafe regions

I would use:

```python
torch.backends.cuda.matmul.allow_tf32 = True
torch.backends.cudnn.allow_tf32 = True
torch.set_float32_matmul_precision("high")
```

And then only autocast **safe regions**:

* safe: feature MLPs, candidate scoring, large matmuls for feature extraction
* unsafe: **BP**, log-domain updates, damping, `linalg.solve` / `lstsq`, BER counters

### Safe pattern

```python
with torch.autocast("cuda", dtype=torch.bfloat16, enabled=args.amp_head):
    logits = c2rel_head(feats)   # safe

with torch.autocast("cuda", enabled=False):
    g = torch.linalg.solve(G.float(), b.float())   # keep fp32
    x = mp_detect_bp_torch(..., dtype=torch.float32)
```

I would prefer **bf16 over fp16** here.

### 4) Batched LS solves

If support sizes are similar, stack Gram systems:

* group frames by support size
* build batched `G = Phi_S^H Phi_S`
* use batched `cholesky_ex + cholesky_solve`

This mostly removes dispatch overhead from many tiny solves.

### 5) CUDA streams: not my first move

On a single 4090, overlapping channel-est and detector compute with streams is **not** where I'd spend time first. Both are GPU-heavy and will contend for the same device.
Streams help more for:

* overlapping **H2D copies**
* overlapping **CPU frame generation** with GPU compute

So my answer is: **low priority**.

### Also worth saying explicitly

* **bucketize LS, not BP**
* `torch.compile` is a possible 6th option, but I'd put it below the five above because complex ops and dynamic control flow can make it annoying
