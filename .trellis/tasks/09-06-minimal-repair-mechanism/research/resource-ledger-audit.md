## 去重和时间口径

1. 优先用各作业 `status.json` 内的 `started_at` 与 `elapsed_seconds`，它们对应导入后至作业内收尾的测量窗口。
2. 无子状态时，用父批次 `runs` 中相应子作业的 start/elapsed。S1 的四项、S2 的 E1 parity 与五项 CPU calibration 属于此类。父进程轮询会给部分尾部时间带来秒级计费余量；这些是作业执行/保留窗口，不是纯计算时间。
3. 父批次整体 `elapsed_seconds` 不再加入。特别是 `refs-batch.json` 在启动 I5 前等待 matrix 约 340.36 秒；这不是额外 GPU 工作。`soft-cuda-batch.json` 的前三项缺子项 start，但对应子状态完整，因此使用子状态，无需推断排队间隔。
4. 只合并 `[start,start+elapsed]` 区间。CPU 与 CUDA 由状态 device、显式 `--require-cuda`，或校准批次 `cuda_visible_devices=''` 判定；没有未知设备的已纳入窗口。
5. 全部纳入子作业均完成。失败的 CPU soft 批次也计入已实际执行的两个子作业；失败不能抹去费用。

## 对剩余额度的限制

S1 上限 3600 秒，S2 上限 14400 秒。在按上述作业窗口并集记账的口径下，“上限减已记账量”分别为：

- S1：机器与 GPU 均为 2099.561 秒（34.993 分钟）。
- S2：机器 11127.705 秒（185.462 分钟），GPU 11339.671 秒（188.995 分钟）。

这些数字只是**未扣缺口前的名义上界**，不是可以直接调度的剩余授权。考虑缺失工作，非负剩余量只能暂记 `0 ≤ remaining ≤ 名义上界`，也不能排除账外工作已耗尽额度。JSON 中 `exact_remaining_seconds` 明确为 null。

另一个必须保持清晰的区别：若原预算中的“machine-wall”实际指阶段开始至结束的连续历时，而非本请求要求的忙碌窗口并集，结论会变化。S1 从已记录 preflight 开始至 budget 结束已跨越 **4281.790 秒（71.363 分钟）**，超过一小时；S2 最早已记账作业至最晚作业为 6249.277 秒（104.155 分钟）。本报告不擅自把连续历时预算改写为忙碌并集预算。

在账本补全或原定义确认前，不能据此宣布 S1/S2 预算门通过，也不能借用未核实的“余额”扩大任务。S3/S4 独立预算应单独持续记录，同样保存 start、end、device、失败与取消状态。
