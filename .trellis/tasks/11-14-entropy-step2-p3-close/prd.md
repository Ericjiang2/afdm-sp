## A 阶段：逐组再审（只读，不改任何文件）

一个输出目录算一组。每组填一行：

1. **是什么**：哪个实验、哪天、文件数、体积、有多少在 git 里、有多少被忽略。
2. **有没有绑定**：全部结果卡（不只当前的）、汇报、预注册协议、`STATE.md`、在做的实验，有没有哪一个指向它。有就写明是哪一个。
3. **有没有定不了的引用可能指向它**：从诊断的引用表里取出静态前缀够得着这一组的那些条目。有一条就不能进删除清单，除非这一条被查清。没有可见前缀的动态路径归不到任何一组，只报总数；它们不能证明这一组没人用，是留给 Eric 知情的剩余风险。
4. **找不找得回来**：三种情况分开写。内容在 vault 仓库某个分支够得着的提交里；能按记录的代码版本和参数重新算出来（要有记录，不是「理论上能」；没有真的重算过就写「未验证」，不算恢复来源）；都不是。远程服务器上有没有另一份，本阶段不连远程，写「没查」。
5. **有没有流程还在往里写**。
6. **建议的去向**，五选一，并写把握（高、中、低）和依据：
   - 补绑定：它其实是某个结果的原始数据，补上指向后长期保留。
   - 保留：还被加载，或者是有保留价值的失败结果。
   - 继续待审：查不清。
   - 打包移出：压成一个包放到工作目录之外，原地留一行存根。
   - 彻底删除：没有任何恢复来源，删了就没了。

`.mission/` 的目录另加一项：里面的源码文件有多少和 vault 仓库已提交的内容逐字节相同（这些可以由 git 取回），有多少是独有的。诊断估计 82% 的 Python 文件是副本，这里按目录给出实数。

## B 阶段：Eric 定

A 阶段交接后停下。要 Eric 定的有四件：

1. 逐组确认或改去向。批准的是这份清单的这个版本。
2. **要不要允许「彻底删除」**。`treatment-plan.md` 第 4 节现在的写法是：没有核对过的恢复来源就不能淘汰。本项目七成多的文件不在 git 里，照这个写法，大部分输出永远删不掉，只能留着或打包。档案管理的原做法里，批准过的处置可以是真的销毁。放不放开这一条，是改规则，由 Eric 定（7.8）。建议：只对再审过、Eric 逐组批准、明确写着「删了就没了」的第 5 类输出放开。
