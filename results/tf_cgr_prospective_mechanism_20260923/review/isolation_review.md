# BLOCK isolation review before the new three-arm prospective run

**Finding:** The frozen BLOCK coordinate error is confined to its own detector call; this review found no numerical state path from BLOCK into later BASE, CGR, or SHAM decisions. The old sealed four-arm run supports that conclusion even when BLOCK ran first. It does **not** establish timing or allocator isolation, and the existing four-arm runner cannot be reused unchanged for the authorized 256-frame, three-arm, at-most-768-call campaign. This is a source and sealed-data review only: zero new frames, receivers, decoders, or trajectory replays.

## Frozen call and import boundary

All 12 source files enumerated in `isolation_review.json` match their actual SHA-256 entries in the committed v2 observed manifest. `run_observed.py` loads the four detector modules once, then selects one module per wrapper through `detectors[arm]` in `_branch`. `tf_base.py`, `tf_cgr.py`, and `tf_sham.py` are separate generated modules from one SHA-bound native `twofft.py`. Their only algorithmic difference is the local `gain_R` contraction in the final TF step: `I`, physical `R`, or the stored-slot same-delay sign conjugation `DᴴRD`. They import the same read-only `physical` and `messages` functions; no BLOCK object or function is called on their detector path. Native TF_J20_R2 imports `native_twofft` and native `twofft` independently of all four final-batch modules.

`tf_block` imports `Basis` from `block_bilinear`, but the module has no import-time receiver call, random draw, or patch of `physical`, `messages`, native TF, or the generated scalar modules. The preflight's `tf_block.bind_source(...)` verifies the block source SHA and assigns only `tf_block.SOURCE_PATH`. The mixed time-observation/AF-response subtraction occurs inside `tf_block.scalar_joint` when and only when the selected arm is BLOCK. The frozen variant generator's production `verify()` reads and compares source/module bytes; it does not regenerate or patch modules.

The wrapper makes fresh `app`, `check`, QPSK moments, time-transformed observation, geometry `Path` list, and `Channel` for each triggered branch. `Channel` is a frozen dataclass and copies delays, Dopplers, and gains on construction. BLOCK constructs local `Basis`, `S`, `h`, `x`, and residual arrays; its source contains no global RNG or writes to the observation, channel, shared LDPC code, or other detector module. The shared decoder routine creates local messages and reads the code's edge arrays. Each wrapper runs its own native prefix and obtains its own native arrays before branch selection. `sink` and output `row` are closure-local per wrapper, and checkpoint/decision paths include the arm. We found no cross-arm numerical mutation route in this frozen call graph.

## Sealed-order check and limits

The old 25-observation schedule rotated arm order: BLOCK preceded BASE on 18 frames, CGR on 12, and SHAM on 6; BLOCK was first on 6. The independent sealed-data verifier reported 25 frames with **zero round-0 bit, round-1 bit, and branch-entering mismatches** across arms, despite those orders. The post-seal main analyzer checked historical BASE final-bit parity on **25/25** saved observations. Its independent truth recount explicitly did *not* repeat that historical comparison and did not check historical LLR parity; the narrower provenance is retained here. Together these are strong evidence that the executed BLOCK branch did not numerically contaminate the later three arms in the old run, but they cannot prove an arbitrary future implementation safe.

BLOCK still consumes CPU time and creates arrays and library/cache state in the four-arm process. The old experiment's clocks therefore cannot certify the timing or memory footprint of a clean three-arm process. `run_observed.py` hard-codes `ARMS=('BASE','CGR','SHAM','BLOCK')`, schedules 100 four-arm calls, and its preflight imports/binds `tf_block`; running it unchanged would violate the new three-arm call budget and retain an unnecessary BLOCK import. A prospective runner may reuse source-verified generic logic, but its *actual* registered schedule/imports and per-arm clock boundaries require a separate prelaunch review. This review is not that approval.

## Prior JVP boundary recheck

The previous offline review covered the BASE analytical JVP's prior-step `mu/v/vh` input timing, post-gain-only arm impulse, full residual/variance/softmax differentiation, one-sided floor and clipping rules, and final gain impulse's zero same-batch LLR effect. I rechecked only the potentially material saved boundary claim: all eight target BASE raw artifacts are SHA-bound in the old seal; their 160 trace rows have **zero data or gain reciprocal-floor activations**, and their terminal extrinsic values have **zero exact ±20 boundary or outside-clip components**. The synthetic first/nonfirst-step derivative qualification and prior full code checks need no repeat. A new prospective analysis should not present this development-trace JVP as automatically validated on fresh states; it must evaluate its predeclared saved-state boundary and evidence checks on those fresh records.

## Gate for the new run

Numerical isolation from BLOCK: **supported for the frozen source and old sealed run**. New three-arm execution: **pending review of its frozen runner/protocol**, including explicit exclusion of BLOCK calls, independent observed-only inputs and native prefixes, source hashes, output directories, and complete clocks. No inference about prospective FER or new timing follows from this review.
