# F0 versus F1 operation and measurement ledger

Source anchor `cd0be005484e1c21fd148f686e08acfc30d567b7`; this is **preimplementation arithmetic**, not measured runtime. F0 is the actual frozen `pilot_front`/`time_refine` sequence. F1 is the [specified challenger](F1_NOMP_AFDM_SPEC.md). Report every cohort both as acquisition-only and as complete coded wrapper; do not equate a correlation count with wall time, memory or deadline availability.

| Component | F0 actual | F1 frozen proposal | Accounting requirement |
|---|---|---|---|
| Admissible initial dictionary | 103 delays × 5 integer Dopplers `−2,...,2` = **515** complex pilot columns | 103 delays × 25 quarter Dopplers `−3,...,3` = **2,575** physical columns | Same delay bound; F1 has a wider/finer Doppler search. Cache only when exact pilot, `N,c1,c2,CPP` hashes match; otherwise construction is per frame. |
| Greedy correlations | `B0-p2-s0.5` passes API capacity 40 but nominates **24** OMP iterations (`supplement_baselines.PARAMETERS['B0'][2]`), unless its residual stopping condition fires. Upper count `24×515=12,360` column-residual products. | Up to eight insertions, each scanning 2,575 candidates: `8×2575=20,600` products before duplicate masking/early numerical stop. | Ratio of those upper counts is **5/3 = 1.667**, not 1. `8×2575 = 40×515` is true arithmetic but compares F1 with an **unexecuted 40-nomination F0 budget**. A complex length-1024 inner product costs O(N), yet implementation dtype, memory traffic, precomputation and BLAS schedule differ. |
| Residual update and gain fitting | Every chosen integer atom invokes `torch.linalg.lstsq` on current support (driver `gels`); upper 24 fits, plus final fit. Leading dense QR/LS work roughly `O(N Σ_{j=1}^{24}j²)` plus selected-column materialization. | Joint ridge solve after each accepted insertion (`≤8`), each accepted Newton coordinate and each cyclic visit. At full eight slots, two cyclic passes per insertion visit `2Σ_{j=1}^{8}j=72` coordinates in addition to eight insertion coordinates; each may propose up to four Newton steps, four backtracks per step, and two endpoints. Up to ~80 coordinate visits and many O(N) response/score evaluations. | Count actual score calls, derivative calls, accepted/rejected visits, joint solves, condition failures, path slots and elapsed time separately. A small P does not make cyclic work free. |
| Grouping/model order | Up to 24 selected coefficients grouped by delay, squared magnitudes summed; top `≤8` groups, one strongest Doppler per delay. Group/sort O(m log m) is minor next to responses/LS, but can discard useful physical components. | No delay grouping; up to eight physical slots, same-delay allowed if `|Δν|≥1e−6`; numerical no-improvement stop only. | Report `P_F0`/`P_F1`, same-delay counts and actual groups. Extra F1 slots, not just multiplicity handling, may explain differences. |
| Pre-TF physical refinement | **One** `time_refine` call per coded round, **two** bounded coordinate passes within each call; it builds `BᴴB+Γ(v)+σ²I`, allows max 16 scalar evaluations per slot, then passes one-center-per-delay geometry to TF. | **One** comparator-only `time_refine_keep_slots` call per coded round with the **same objective and pass/evaluation limits**, preserving every F1 slot; repeated delay makes off-diagonal Gram/Γ terms material. | Charge both complete coded rounds, their transforms/response construction, `P×P` solves, rejected candidates, and adapter overhead. Never route F1 through destructive `np.unique`. |
| Downstream TF/LDPC and evidence | Two TF20 rounds, LDPC50 after each; check/APP messages, checkpoints, raw serialization and ledger. B adds CSTATE only on nonzero final syndrome. | C uses same TF/LDPC; D adds the same CSTATE trigger/branch after F1 geometry. Same scalar gain approximation even when same-delay `R≠I`. | Measure complete wrapper mean/median/p95/p99/max, 0.5/1.0 s latest-ready decision, branch-only work, and all serialization/hash. Different trigger rates change average cost. |

One materialized complex128 `N×M` bank at `N=1024` is **8,437,760 bytes** for F0's 515 columns and **42,188,800 bytes** for F1's 2,575; a complex64 copy is half each. F0 actually builds NumPy physical columns and copies to Torch complex64, so peak is not one table. F1 may stream or cache pilot responses, but must measure transient arrays, derivative workspaces, RSS/peak state and cache ownership. `y`, residual, `B`, Gram, source transforms, Torch conversion and evidence buffers belong in the ledger. Precomputed pilot/system-only columns may amortize over identical pilot hashes; per-frame `y`, residual, gain solves, Newton decisions, and coded continuations cannot.

No measured F1 runtime, energy or memory exists. The candidate is only **plausibly** low complexity in path order (`P≤8`) and may still be slower than F0 because its correlation bank is 5× wider per scan, Newton/line-search work is additional, and duplicate-preserving refit changes cache locality. Runtime fairness also requires the exact same CPU, thread count, dtype policy, warmup scope, clocks, serializer and deadline origin for A/B/C/D; no historical F0 timer may be pasted beside a new F1 timer.
